# Рабочий процесс ChatGPT → GitHub → Kimi

Этот каталог — единственный источник задач по этому проекту.

## Роли

- **Артём** определяет приоритет и принимает результат.
- **ChatGPT** формулирует ТЗ и публикует его в `tasks/`.
- **Kimi** забирает только задачу, указанную в `tasks/ACTIVE.md`, выполняет её, обновляет статус в файле задачи, коммитит код и отчёт.

## Статусы

Использовать только эти значения:

- `draft` — ТЗ ещё формируется, выполнять нельзя.
- `ready` — ТЗ утверждено и готово к работе.
- `in_progress` — Kimi начал выполнение.
- `blocked` — работа остановлена; в разделе `Блокеры` обязательно указать причину и что требуется от Артёма.
- `review` — код и deploy готовы, требуется проверка Артёма/ChatGPT.
- `done` — задача принята.
- `cancelled` — задача отменена.

## Правила для ChatGPT

1. Создать файл `tasks/TASK-XXX-kebab-name.md` по шаблону `tasks/TASK_TEMPLATE.md`.
2. Указать точный `base_commit` текущей ветки `main`.
3. Поставить `status: ready` только после окончательного согласования ТЗ.
4. Обновить `tasks/ACTIVE.md`, указав ровно одну активную задачу.
5. Не редактировать исходный код в рамках постановки ТЗ.
6. Новые уточнения добавлять в тот же файл задачи в раздел `Уточнения`, не создавать параллельные противоречащие ТЗ.
7. Push в `main`, меняющий `tasks/ACTIVE.md` или `tasks/TASK-*.md`, автоматически запускает Kimi (GitHub Action), если у активной задачи `status: ready`. Поэтому `status: ready` ставить только в финальном коммите ТЗ.

## Правила для Kimi

1. Работа ведётся только в ветке `kimi/<TASK-ID>`. В `main` напрямую не коммитить и не пушить. При автоматическом запуске (GitHub Action) ветка уже создана и текущая — ничего переключать не нужно. При ручном запуске: `git pull origin main`, затем `git checkout -B kimi/<TASK-ID> origin/main`.
2. Открыть `tasks/ACTIVE.md`, затем указанный файл задачи.
3. Не выполнять задачи со статусом `draft`, `done`, `cancelled` или не указанные в `ACTIVE.md`.
4. До изменения кода обновить в файле задачи:
   - `status: in_progress`;
   - `started_at`;
   - `worker: Kimi`;
   - фактический стартовый SHA.
5. Сделать отдельный первый коммит только со сменой статуса: `task(TASK-XXX): start`.
6. Работать строго в рамках `Разрешено менять` и `Не менять`.
7. Если ТЗ противоречит коду или не хватает данных — не додумывать. Поставить `status: blocked`, описать вопрос и закоммитить: `task(TASK-XXX): blocked`.
8. После реализации:
   - выполнить проверки из ТЗ;
   - deploy на test2, если это предусмотрено;
   - обновить `Результат выполнения`;
   - указать commit SHA, версию, изменённые файлы, тесты, известные ограничения;
   - поставить `status: review`;
   - закоммитить отчёт вместе с итоговыми изменениями либо отдельным коммитом `task(TASK-XXX): ready for review`;
   - push ветки и создание Pull Request в `main` выполняет автоматика (GitHub Action) — вручную push делать не нужно.
9. Не ставить `done` самостоятельно. `done` ставится только после приёмки Артёмом/ChatGPT.
10. Не переписывать историю, не использовать force push, не удалять чужие файлы и не смешивать несколько задач в одном коммите.

## Формат коммитов

- `task(TASK-XXX): start`
- `fix(TASK-XXX): краткое описание`
- `feat(TASK-XXX): краткое описание`
- `docs(TASK-XXX): update status report`
- `task(TASK-XXX): blocked`
- `task(TASK-XXX): ready for review`

## Приёмка

После статуса `review` ChatGPT/Артём:

1. Проверяет Pull Request `kimi/TASK-XXX` → `main` (diff от `base_commit` до итогового SHA).
2. Проверяет live-сайт и критерии приёмки.
3. При замечаниях дописывает их в раздел `Замечания при проверке` и возвращает `status: ready` — задача будет автоматически запущена повторно в той же ветке.
4. При успешной проверке мержит PR в `main`, ставит `status: done`, заполняет `accepted_at` и очищает `tasks/ACTIVE.md`.

## Важное правило

Содержимое файла задачи важнее сообщений в чатах. Если чат и GitHub расходятся, Kimi должен остановиться и запросить обновление ТЗ в GitHub.
